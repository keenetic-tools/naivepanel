# Self-update: надёжное завершение, retry и восстановление после reboot

Дата: 2026-11-22. Статус: дизайн согласован и реализован, релиз не публиковался.

## Понимание задачи

- Исправить завершение self-update: установщик не должен оставлять zombie, а
  панель обязана сохранять код возврата и понятную причину сбоя.
- Разрешить ручной retry сразу после сбоя, не ожидая 15-минутного stale TTL.
- После внезапной перезагрузки роутера не доверять сохранённому pid: он мог
  быть повторно использован другим процессом.
- Сделать диалог обновления понятным: статус, причина, код ошибки, актуальный
  релиз и явное следующее действие важнее двух больших логов.
- Проверить настоящий self-update в Docker/Entware, включая падение, retry,
  смену версии и перезапуск панели.
- Текущий UI в целом сохраняется. Полный редизайн — отдельная будущая задача
  в `docs/ROADMAP.md`.
- Не публиковать новый релиз, не менять опубликованные release notes и не
  создавать теги в рамках этой итерации без отдельной команды.

## Ограничения и допущения

- Цель — Entware/Linux на роутере с ограниченной памятью; обновления редкие,
  один daemon waiter на попытку допустим.
- Один администратор, но возможны две вкладки и параллельные API-запросы.
- Runtime остаётся stdlib + существующие Flask/Waitress; UI — vanilla JS/CSS,
  нативный `<dialog>`, без CDN, фреймворков и browser-зависимостей в проекте.
- Автоматический retry запрещён: ошибки сети, подписи и диска требуют явного
  действия пользователя.
- Обновление панели не должно прерывать работу `naive`.
- Старые state-файлы без `boot_id`, `exit_code` и `error` остаются валидными.
- Полная power-loss-safe замена набора файлов не входит в итерацию: сейчас
  `install.sh` удаляет package-каталог и копирует файлы последовательно.
  Отключение питания в этой точке может потребовать восстановления через SSH.
  Это отдельная P1 roadmap-задача.

## Backend

### Запуск и waiter

1. `POST /api/update/apply` выполняет существующие auth/CSRF и release checks.
2. Под `_UPDATE_LAUNCH_LOCK` reconciler проверяет состояние, installer spawn'ится,
   `running` с `target`, `started`, `pid`, `boot_id` записывается атомарно.
   Shell-обёртка логирует код установщика и явно завершается `exit "$rc"`, чтобы
   последний `echo` не маскировал сбой нулевым статусом.
3. После записи state запускается daemon waiter с `Popen`-объектом; пара
   `(pid, started)` регистрируется до старта потока, чтобы reconciler не
   объявил zombie мёртвым до того, как waiter сохранит настоящий код.
4. Ответ 202 дополнительно содержит `attempt_started` (значение state `started`)
   и `pid`; прежние поля сохраняются, `started: true` подтверждает запуск.
5. `_UPDATE_LAUNCH_LOCK` становится `RLock`: reconciler, launch и финальная
   compare-and-write операция waiter используют один порядок сериализации.

Waiter единолично вызывает `proc.wait()`:

- `rc != 0`: если state всё ещё относится к той же попытке (`phase=running`,
  тот же `pid` и `started`), записать `phase=failed`, `finished`, `exit_code=rc`,
  `error="installer exited with code N"`.
- `rc == 0`: state остаётся `running`. Новая версия после штатного рестарта
  отметит `done`. Если установщик завершился без рестарта, reconciler старой
  панели обнаружит мёртвый pid и отметит `failed`.
- Если state уже относится к другой попытке, waiter ничего не записывает.

`_pid_alive()` больше не вызывает `waitpid`: на Linux читает состояние из
`/proc/<pid>/stat`, включая `Z`; при отсутствии `/proc` использует прежний
`os.kill(pid, 0)`. Это неразрушающий fallback для reboot/legacy state, а не
владелец дочернего процесса.

### Перезагрузка и долговечность state

Boot ID читается из `/proc/sys/kernel/random/boot_id`; на платформе без него
поле отсутствует и действует legacy fallback.

Для `phase=running` reconciler действует в порядке:

1. `target == APP_VERSION` → `done` (штатный запуск новой версии).
2. Сохранённый и текущий boot ID заданы и различаются → `failed`,
   `error="update interrupted by router reboot"`, `finished`; pid не проверяется.
3. Мёртвый/zombie pid → `failed` с `finished` и понятной ошибкой.
4. Живой pid и превышение stale TTL → `stale=true`, как раньше.

`_update_state_write` после `_save_json` дополнительно делает `fsync` каталога
state-файла, чтобы сохранить rename при внезапном отключении питания. Ошибки
записи по-прежнему не роняют работающий installer, но логируются.

## UI

Диалог сохраняет существующий `<dialog>` и переиспользование для naive/rollback.

- Заголовок «Обновление панели» и строка состояния с `role=status`.
- При сбое компактный error-блок содержит причину и `exit_code`, если он есть.
- UI принимает `failed` только при совпадении `pid` и `state.started` с `pid`
  и `attempt_started` из ответа apply.
- Лог installer — в `<details>` с ограниченной высотой; во время обновления и
  после ошибки открыт. Лог панели — отдельный `<details>`, по умолчанию свёрнут.
- После сбоя автоматически выполняется `checkUpdate(true)`, как в v0.27.3.
- Кнопка «Проверить релиз и повторить» показывает ход проверки, затем
  актуальную версию. Запуск повторной попытки требует подтверждения.
- При ошибке проверки доступно «Повторить проверку»; stale apply не запускается.
- Состояния для обновления naive и rollback сбрасываются отдельно, чтобы новые
  элементы панели не появлялись в этих сценариях.
- Тап-цели ≥44px на mobile, видимый фокус, нет горизонтального скролла,
  обе темы используют существующие токены.

## Тестирование

### Unit/API

- Waiter записывает ненулевой `exit_code`, `finished` и `error`.
- Старый waiter не перезаписывает state новой попытки.
- Нулевой rc не превращается в преждевременный `done` без новой версии.
- Изменённый boot ID даёт `failed` даже при живом совпадающем pid.
- Целевая версия после reboot имеет приоритет и даёт `done`.
- Legacy state без boot ID/exit_code обрабатывается без ошибок.
- Retry после failed возвращает 202, параллельный живой update — 409.
- Contract-тесты проверяют новые элементы dialog и отсутствие регрессий
  naive/rollback.

### Docker Entware E2E

- Fake release API отдаёт следующий тестовый тег.
- Тестовый тег имеет изменённый `APP_VERSION`, собственный `SHA256SUMS` и
  подпись временным тестовым ключом. Оба served-релиза (рабочая копия может
  отличаться от опубликованной подписи) пересчитываются и подписываются этим
  ключом, а test public key подставляется только в их served installer'ы.
  Файлы репозитория и настоящий release key не используются и не изменяются.
- Первый apply специально завершается кодом 3 до изменения файлов. E2E ждёт
  `failed`, проверяет `exit_code=3`, затем повторяет apply.
- Вторая попытка проходит настоящий installer, проверку подписи, замену файлов,
  restart и смену версии; новый state становится `done`.
- Отдельный Linux-сценарий создаёт zombie, чужой для проверяющего процесса, и
  подтверждает обнаружение `Z` через `/proc`.
- Перед созданием release tag тот же workflow запускается через
  `workflow_dispatch` на release candidate; существующие tag/nightly runs
  сохраняются. README описывает этот порядок.

### Живой UI

Проверить running/failed/retry/update-check-error в desktop и mobile, dark/light;
