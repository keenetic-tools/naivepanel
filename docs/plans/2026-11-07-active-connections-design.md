# 2.2 — Счётчик активных соединений: дизайн

**Статус:** базовая версия вошла в v0.22.0; уточнённая семантика
(loopback в `established`, `clients` — только прямые) — в v0.22.1.
**Roadmap:** пункт 2.2, приоритет P2.

## Understanding summary

- В `/api/status` добавляется снимок активных соединений активного пресета:
  число ESTABLISHED и число уникальных прямых клиентских IP.
- Источник данных — `/proc/net/tcp` и `/proc/net/tcp6`, парсинг stdlib.
  Внешние утилиты (`ss`, `netstat`, `conntrack`) не используются: на OpenWrt
  их нет по умолчанию.
- Считаются сокеты в состоянии `01` (ESTABLISHED), у которых local-порт
  входит в множество listen-портов активного пресета.
- `established` включает loopback: за локальным форвардером (xray и т.п.)
  реальные клиенты видны только как `127.0.0.1`, и без них счётчик терял бы
  всю нагрузку. `clients` — только не-loopback адреса (прямые клиенты);
  при loopback-only listen loopback считается и клиентом.
- UI — одна строка «соединений» в карточке «Обзор», обновление вместе
  с текущим poll раз в 3 секунды. Отдельного таймера и фонового потока нет.
- Ошибка чтения `/proc`, отсутствие активного пресета или listen → `null`;
  `/api/status` при этом остаётся успешным.

**Зачем:** дешёвый ответ на вопрос «прокси сейчас кто-то использует?»
без полноценного мониторинга и без изменений в naive.

**Кому:** владельцу роутера, сценарий «роутер держит прокси всего дома».

## Допущения

- Панель и naive работают в одном network namespace (нативный запуск
  на роутере). Контейнерный/namespace-сценарий не покрывается.
- listen у naive — только TCP.
- Нагрузка — десятки-сотни соединений; чтение двух файлов на каждый poll
  пренебрежимо на фоне остальной работы `_status()`.
- Наружу отдаются только числа; IP клиентов не попадают ни в API, ни в DOM.
- Внешние (не-LAN) клиенты, если listen доступен извне, считаются
  обычными клиентами.

## Decision Log

| # | Решение | Альтернативы | Почему |
|---|---------|--------------|--------|
| 1 | Источник — `/proc/net/tcp{,6}` | `ss`, BusyBox `netstat`, `/proc/net/nf_conntrack` | `/proc` есть всегда, читается без root, не зависит от пакетов OpenWrt и форматов BusyBox |
| 2 | Показывать соединения + уникальных клиентов (уточнено в 11: в UI остались только соединения) | только соединения; таблица по клиентам | Одно число соединений не отвечает на вопрос «сколько устройств»; таблица выходит за рамки «дешёвого снимка» |
| 3 | Данные в `/api/status`, обновление раз в 3с | отдельный endpoint и карточка; только API | Нулевая цена: статус уже поллится, отдельный таймер и UI-блок не нужны |
| 4 | Loopback исключать из клиентов, но не из соединений (уточнено в 11) | исключать везде; считать всё клиентами | После v0.22.0 выяснилось: xray форвардит клиентов на `127.0.0.1`, и исключение loopback из соединений теряло почти всю нагрузку |
| 5 | Читать `/proc` на каждый запрос, без кэша и потока | TTL-кэш 2–3с; сэмплирование в монитор-потоке | Нет состояния, тестов и рассинхронизации; стоимость чтения ничтожна. Кэш и поток — YAGNI для одного админа |
| 6 | Все listen-адреса пресета, а не только первый | первый адрес, как в `_active_listen()` | Массив listen — легальная конфигурация; объединение портов стоит одну строку |
| 7 | `allow_loopback` только если *все* listen-хосты loopback | если хотя бы один; всегда false | Смешанная конфигурация означает, что реальный трафик идёт не только по loopback |
| 8 | `::ffff:a.b.c.d` нормализуется в IPv4 | считать как разные адреса | Один клиент не должен задваиваться между `tcp` и `tcp6` |
| 9 | Ошибки → `null`, статус 200 | 500; скрывать поле | Счётчик диагностический, он не должен ронять основной статус |
| 10 | Regression-first: парсер и `snapshot` тестируются на файлах-фикстурах | мокать чтение `/proc` | Чистый парсер + явные пути дают детерминированные тесты без monkeypatch |
| 11 | `established` считает loopback; `clients` — только прямые; UI показывает одно число | исключать loopback везде; показывать клиентов всегда | Реальный сценарий: перед naive стоит xray, все клиенты приходят с `127.0.0.1`. Уникальные устройства посчитать нельзя, но нагрузку — можно; `clients=1` в UI вводил бы в заблуждение |

## Final design

### Модуль `panel/connections.py`

Без импортов из `monitor`/`presets` — направление зависимостей только
`monitor → connections`.

```python
def parse_proc_net(text: str) -> Iterator[tuple[int, str, str]]:
    """Строки /proc/net/tcp{,6} → (local_port, remote_ip, state)."""

def snapshot(ports: set[int], allow_loopback: bool,
             tcp_path: Path = Path("/proc/net/tcp"),
             tcp6_path: Path = Path("/proc/net/tcp6")) -> dict | None:
    """{"established": N, "clients": M} или None, если /proc недоступен."""
```

- Парсер пропускает заголовок и битые строки.
- IPv4-адрес в `/proc` — little-endian hex; IPv6 — 4 слова по 32 бита,
  также little-endian. Mapped-адреса приводятся к IPv4.
- `snapshot` фильтрует `state == "01"` и `local_port in ports`;
  `established` считает все совпадения, `clients` — множество remote IP,
  куда loopback попадает только при `allow_loopback=True`.
- Если не читается ни один файл — `None`; если один — частичный результат.
- Валидность IP проверяется через stdlib `ipaddress`; невалидные
  пропускаются.

### Интеграция в монитор

- `_active_listen_uris()` — все listen-адреса активного пресета
  (строка или массив) из `config.json`.
- `_active_listen_ports()` — через существующий `_listen_endpoint`:
  множество портов + `allow_loopback` = «все хосты loopback».
- `_status()` добавляет:

```json
"connections": {"established": 3, "clients": 2}
```

  или `null`. Вызов обёрнут в `try/except Exception`, чтобы сбой счётчика
  не ломал статус.

### UI

В `renderStatus()` — одна строка в `svcinfo` после `pid`:

```text
соединений   19
```

- При `null` — `—`.
- `title` строки: «ESTABLISHED на listen-портах активного пресета,
  включая локальный форвардер».
- При остановленном прокси — `0` (честный ноль, не отсутствие данных).
- IP-адреса в DOM не выводятся; `clients` остаётся только в API.

### Ошибки и края

- Нет `/proc` (macOS/BSD), `PermissionError`, пустой файл → `None`.
- Битые строки, невалидные hex/порты — пропускаются по одной.
- Отсутствует только `tcp6` или только `tcp` → работаем по доступному.
- Нераспознанный listen-URI игнорируется; если портов не осталось → `None`.
- Учитывается только ESTABLISHED; LISTEN, SYN_RECV, TIME_WAIT — нет.
- Дубли портов в listen-URI не задваивают счётчик (множество).
- E2E-пробы панели (loopback) добавляют кратковременный +1 к `established`;
  для счётчика нагрузки это приемлемо, из `clients` они исключены.

### Тесты (regression-first)

1. `parse_proc_net`: IPv4, IPv6, mapped, битые строки, разные state.
2. `snapshot` на временных файлах: фильтр портов/состояний, loopback
   в `established`, но не в `clients`, сценарий xray (19 соединений / 1
   прямой клиент), частичное отсутствие файлов, оба отсутствуют → `None`.
3. `_active_listen_ports()`: строка/массив, дефолтные порты,
   невалидный URI, loopback-only.
4. `_status()`: поле присутствует; при сбое snapshot — `null`,
   статус не падает.
5. HTML-тест в существующем стиле: строка «соединений» есть, «клиентов»
   в UI нет; title упоминает локальный форвардер.
6. Linux-only интеграционный тест: реальный listen-сокет + клиент →
   `established >= 1`; на macOS skip.

## Non-goals

История и пики соединений, таблица по клиентам, графики трафика,
фоновый поток сэмплирования, внешние утилиты, изменения в naive.
